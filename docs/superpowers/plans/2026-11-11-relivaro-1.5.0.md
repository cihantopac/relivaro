# Relivaro 1.5.0 Integration and Hosted Scanning Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make Relivaro safe and predictable to embed in CI and in hosted scanners (Frameva runs it on uploaded archives with no network): bounded runs, hard lockdown, documented contracts, privacy controls and better SARIF. Ship as `relivaro@1.5.0`.

**Precondition:** 1.4.0 is released (`docs/superpowers/plans/2026-11-11-relivaro-1.4.0.md`). This plan builds on its `--no-gitignore`, `--assume-tracked` and `--no-inline-suppressions` flags.

**Architecture:**
- A new `src/core/limits.ts` holds a run budget that `runAudit` and the engine file loop check.
- Process signals are handled in `src/cli/main.ts`. They write a partial record.
- Lockdown is resolved once in `src/cli/commands.ts`, before any command runs.
- Contracts are added as data files and checked in tests:
  - a JSON Schema for the run record
  - a JSON contract fixture
  - a programmatic entry point built by esbuild next to the bin
- Nothing here changes what a rule finds.

**Tech Stack:** as 1.4.0, plus a second esbuild entry (`plugin/dist/api.mjs`) and a hand-written `.d.ts`.

**Rulings already made (planner):**
- **Exit code 4 means partial.** It is new; 0, 1, 2 and 3 keep their meaning. Check `docs/CLI.md` for the current table before writing; if 4 is taken, use the next free code and record a ruling.
- **Lockdown is opt-in.** It never changes defaults, so existing CI keeps working.
- **No generated schema tooling.** The run schema is written by hand and pinned by a test that validates real run records from every fixture, so no dependency is added. The validator is a small JSON Schema subset checker in `tests/helpers/`.
- **`--since` without git is a usage error (exit 2).** It must not fall back silently to a full report.

## Global Constraints

The Global Constraints of the 1.4.0 plan hold, with version `1.5.0`. In addition:
- **Partial runs.** A partial run must never look clean. `partial: true` puts a limitation first and forces the release verdict to `NOT VERIFIED` at best.
- **Lockdown.** Under lockdown, no child process is spawned and no socket is opened. Test this with a spy on `child_process.spawn` and on `globalThis.fetch`.

## Review Focus

1. **SIGTERM during the OSV stage or the write of run.json.** The partial record must be written atomically: write to a temp file, then rename. It must never leave half a JSON file. Test in Task 3.
2. **`--max-files` smaller than the number of root metadata files.** The manifests and lockfiles are still read first, so the dependency inventory does not vanish. Test in Task 3.
3. **`--root-label` with a finding message that quotes the absolute path** (e.g. a path-traversal message). Messages and snippets are rewritten too. Test in Task 5.
4. **`--lockdown` together with an explicit `--allow-exec`.** This is a usage error, never "lockdown wins silently". Test in Task 4.
5. **`--since` with a renamed file.** Findings in the renamed file are reported as changed. Test in Task 10.
