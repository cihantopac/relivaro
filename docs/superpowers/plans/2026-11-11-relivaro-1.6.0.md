# Relivaro 1.6.0 New Rule Families Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add the new detections that the Frameva field reports asked for and that can be made precise, and ship them as `relivaro@1.6.0`. The rules cover:
- SSRF defences that compare hostnames without canonicalising them
- URL checks that are bypassed by redirects
- polling loops with no bound
- SQL grants that contradict an append-only table

**Precondition:** 1.5.0 is released. In particular, the coverage line from 1.5.0 Task 9 must exist, because new rules have to be visible in it.

**Architecture:**
- Three AST rules go into the existing modules: `src/rules/security/code.ts` and `src/rules/reliability.ts`.
- One project rule goes into a new `src/rules/security/sql.ts`. It works on `.sql` files, which `classify` already knows (`src/fs/files.ts:154`).
- Each rule gets a fixture with positive cases and their negative twins. Detection stays at 100% precision and recall.

**Tech Stack:** as 1.4.0.

**Rulings already made (planner): these Frameva asks are not built.** Each would be a heuristic with a high false-positive rate, against the user's priority of no wrong findings. They are listed in the changelog under "Considered, not added", with the reason given here.
- **Write-then-record ordering** (b-05): it needs knowledge of transactions and idempotency that a static pass does not have.
- **A try block that wraps more than the call it guards** (b-04): there is no reliable signal for what the guard is for.
- **RLS tenant context** (b-04, b-05): the policies and the `set_config` calls live in different files and in runtime state.
- **DB timestamp vs JS clock comparison** (b-11): types are not known.
- **A forwarding-header guard behind a framework that adds those headers** (c-02): this is framework runtime behaviour.
- **A dynamic `import()` with a computed specifier** (c-02): it is legitimate in most code; an info note would be noise.
- **A generic SHA-1/MD5 rule** (fixture runs): carried over from the 1.4.0 ruling.
- **A hand-written archive parser** (engines run 2): 1.4.0 Task 9 covers entry names that reach file-system calls; byte-level parsers are not recognisable.

Cost if wrong: Frameva keeps finding these by tests, as it does today.

## Global Constraints

The Global Constraints of the 1.4.0 plan hold, with version `1.6.0`. In addition:
- Every new rule has `confidence: 'medium'` or `'low'`, never `'high'`, until it has field evidence from at least two real repositories.
- Every new rule has `description`, `impact`, `recommendation` and `verification` in the style of the existing rules, and appears in `docs/RULES.md` through the build.
- No new rule fires in test files (`ctx.file.isTest`).

## Review Focus

1. **A canonicalising guard in a helper the checking function calls.** For example, `isPrivate(host)` defined in another file, which uses `net.BlockList`. R1 must not fire when the comparison happens inside a function named like a guard that calls `BlockList`, `ipaddr`, `net.isIP` or `dns.lookup`. Test in Task 1.
2. **`redirect: 'manual'` passed through a spread options object** (`fetch(u, { ...base, redirect: 'manual' })`, or `const opts = {redirect:'manual'}`). It is not reported. Test in Task 2.
3. **A polling loop bounded by `AbortSignal.timeout(ms)` passed to the sleep.** It counts as bounded. Test in Task 3.
4. **A `GRANT` in one migration and the append-only trigger in a later migration.** It is still matched, because the SQL set is the whole repository. Test in Task 4.
5. **A quoted or schema-qualified table name** (`"public"."ledger"`, `public.ledger`). It is matched with the bare name. Test in Task 4.

### Task 1: `sec/ssrf-hostname-denylist`

**Files:**
- Modify: `src/rules/security/code.ts` (new rule next to `ssrf` :446, registered in the export list :1820)
- Create: `fixtures/projects/node-api/src/ssrf-guards.ts`
- Test: detection corpus

**Interfaces:**
- Produces: rule `sec/ssrf-hostname-denylist`, severity medium, confidence medium, CWE-918, OWASP A01 (use the `OWASP` constant the `ssrf` rule uses).
- Message: ``Hostname from `new URL(...)` is compared with `${literal}` without IP canonicalisation; `${example}` reaches the same address.``
  - The `example` is chosen from the literal: `127.0.0.1` maps to `2130706433`; `169.254.169.254` maps to `0xa9fea9fe`; `localhost` maps to `127.1`.

- [ ] **Step 1: Write the fixture cases.**
  - Positive cases:
    - `if (new URL(u).hostname === '127.0.0.1') throw …`
    - `const h = new URL(u).hostname; if (['localhost','169.254.169.254'].includes(h)) …`
    - `if (url.host.startsWith('10.')) …` where `url = new URL(x)`
  - Negative twins:
    - the same comparison inside a function that also calls `net.isIP(h)`, `new BlockList()`, `ipaddr.parse(h)` or `dns.lookup(h)`
    - a guard helper with such a call (Review Focus 1)
    - comparing a hostname with an allow value: `=== 'api.example.com'`, which is a domain allowlist, not a deny check
- [ ] **Step 2: Run the corpus and confirm it fails.**
  - Run: `npx vitest run tests/integration/detection.test.ts -t node-api`
  - Expected: one FN per positive case.
- [ ] **Step 3: Implement.**
  - Find `member_expression` nodes with property `hostname`/`host` whose object is `new URL(...)`, or an identifier bound to it.
  - Report a comparison (`===`, `==`, `includes`, `startsWith`, `endsWith`, `test`) against a literal that is an IPv4/IPv6 literal, `localhost`, or an IPv4 prefix.
  - Skip the report when the enclosing function, or a function it calls in the same file, references `isIP`, `BlockList`, `ipaddr`, `lookup`, or `isPrivate…` together with one of those.
- [ ] **Step 4: Run the corpus and confirm it passes.**
  - Run: `npx vitest run tests/integration/detection.test.ts`

### Task 2: `sec/ssrf-redirect-bypass`

**Files:**
- Modify: `src/rules/security/code.ts`
- Modify: `fixtures/projects/node-api/src/ssrf-guards.ts`
- Test: detection corpus

**Interfaces:**
- Produces: rule `sec/ssrf-redirect-bypass`, severity medium, confidence low, CWE-918.
- It fires when, in one function, a URL variable is passed to a guard call and then to `fetch`, `axios(...)`, `axios.get/post/request`, `got`, or `undici.request`/`fetch` without disabling redirects.
  - A guard call is a callee matching `/^(?:assert|check|validate|verify|ensure|is)\w*(?:Url|Host|Target|Safe|Allowed|Public)/i`, or a function containing a Task 1 pattern.
  - Redirects are disabled by `redirect: 'manual' | 'error'`, `maxRedirects: 0`, or `followRedirect: false`.
- Message: ``\`${url}\` is checked by \`${guard}\` and then fetched with redirects enabled; a redirect to an internal address skips the check.``

- [ ] **Step 1: Write the fixture cases.**
  - Positive cases:
    - `await assertPublicUrl(u); await fetch(u)`
    - `validateTarget(u); await axios.get(u)`
  - Negative twins:
    - `fetch(u, { redirect: 'manual' })`
    - a spread or identifier options object that sets it (Review Focus 2)
    - `axios.get(u, { maxRedirects: 0 })`
    - a `fetch` with no prior guard (the existing `sec/ssrf` rule owns that case)
    - an undici `Agent`/dispatcher with `connect.lookup` pinned: `fetch(u, { dispatcher })` where `dispatcher` is built with a `connect: { lookup }` option in the same file. The check then happens at connect time on every hop.
- [ ] **Step 2: Run the corpus and confirm it fails.**
  - Run: `npx vitest run tests/integration/detection.test.ts -t node-api`
  - Expected: FNs for the positive cases.
- [ ] **Step 3: Implement.**
  - Resolve the options object through `pairValue`, plus an identifier lookup to a same-scope `const` object literal.
  - A spread that cannot be resolved counts as "unknown" and is not reported.
- [ ] **Step 4: Run the corpus and confirm it passes.**
  - Run: `npx vitest run tests/integration/detection.test.ts`
  - Expected: PASS.

### Task 4: `sec/sql-grant-append-only`

**Files:**
- Create: `src/rules/security/sql.ts` (project rule over every `.sql` file; registered in `src/rules/index.ts`)
- Create: `fixtures/projects/sql-migrations/` (`migrations/001_ledger.sql`, `002_grants.sql`, `003_trigger.sql`, `.expect.json`)
- Test: detection corpus, `tests/unit/engines.test.ts` (`describe('sql grants')`)

**Interfaces:**
- Produces:
  - `function sqlStatements(text: string): { sql: string; line: number }[]`. It splits on `;` outside quotes, dollar-quoted bodies (`$$…$$`, `$tag$…$tag$`) and comments.
  - Rule `sec/sql-grant-append-only`, severity medium, confidence medium, CWE-732.
- A table is append-only when the SQL set has a `CREATE TRIGGER … BEFORE UPDATE OR DELETE ON <t> … EXECUTE FUNCTION <f>` (in either order of `UPDATE`/`DELETE`), and `<f>`'s body contains `RAISE EXCEPTION`.
- It reports two kinds of grant:
  - `GRANT UPDATE|DELETE|ALL … ON [TABLE] <t> TO <role>`: the grant contradicts the trigger, and a role that owns or can disable triggers escapes it.
  - `GRANT INSERT ON [TABLE] <t> TO <role>` with no column list: it is table-wide, so the role can insert any value, including amounts.
- Message: ``Role \`${role}\` gets table-wide \`${priv}\` on append-only table \`${t}\` (${file}:${line}); limit it to the columns the role must write, or insert through a SECURITY DEFINER function.``
- Table names are compared after removing quotes and the schema prefix (Review Focus 5).

- [ ] **Step 1: Write the failing tests.**
  - `sqlStatements` keeps a `$$ … ; … $$` body intact, and ignores `--` and `/* */` comments.
  - The fixture's expectations:
    - `GRANT INSERT ON ledger TO worker` in `002` reports, even though the trigger is in `003` (Review Focus 4).
    - `GRANT INSERT (account_id, note) ON ledger TO worker` does not report.
    - `GRANT SELECT ON ledger TO reader` does not report.
    - `GRANT INSERT ON other TO worker` does not report: `other` has no trigger.
- [ ] **Step 2: Run them and confirm they fail.**
  - Run: `npx vitest run tests/unit/engines.test.ts -t "sql grants" tests/integration/detection.test.ts -t sql-migrations`
  - Expected: FAIL.
- [ ] **Step 3: Implement** `src/rules/security/sql.ts`.
- [ ] **Step 4: Run them and confirm they pass.**
  - Run: `npx vitest run`
  - Expected: PASS.
- [ ] **Step 5: Commit.**
  - `git commit -m "feat(rules): sec/sql-grant-append-only"`
